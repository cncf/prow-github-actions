# v3.5.0

A hardening release: authorization gaps closed, commands that fail now say so, fewer GitHub API
calls per event, and an App server that survives bad input, slow handlers and rolling updates.
`@v3` callers get it automatically; `@v3.4.0` pins move to `@v3.5.0`.

## Commands

- **Authorization.** `/unassign @user` and `/uncc @user` now require the commenter to be an org
  member or repository collaborator (self-unassign and self-uncc are unchanged). `/remove` refuses
  `lgtm`, `approved`, `hold` and `do-not-merge/*` labels and points to the cancel command. Commands
  run only on a *created* comment; editing an old comment no longer re-runs it.
- **Exclusive label families** (`/priority`, `/lifecycle`, `/stage`, `/status`, `exclusive: true`)
  take one value; `/priority low high` is refused and the issue is left untouched.
- **Exact cancel matching.** `/lgtm cancel`, `/hold cancel` and `/approve cancel` are a cancel only
  when the whole argument is `cancel`; a sentence that merely contains the word no longer removes a
  label. `LGTM` on a repository that spells the label that way now cancels.
- **Refusals are reported.** A refused `/close`, `/reopen`, `/retitle` or self `/assign` fails the
  run with `<user> is not authorized to …`, like `/lock` and `/milestone`; when several commands in
  one comment fail, every failure is reported. `/approve`, `/cc` and `/uncc` on an issue reply that
  they only apply to pull requests.
- `/milestone` pages through all open milestones; `/retitle` validates its title (1–256 chars).

## Plugins and cron jobs

- One bad item no longer aborts the run: the sweep, tide, blunderbuss, the lgtm cron and the App's
  per-installation schedule each isolate per-item failures and continue.
- The bot resolves its own identity from the token instead of assuming `github-actions[bot]`, so
  under a GitHub App tide dequeues the entries it enqueued, `/approve cancel` finds its own review,
  and the approve plugin ignores its own label writes.
- blunderbuss skips users who already reviewed and counts requested teams toward
  `max_request_count`. OWNERS rules survive a truncated tree listing. A deleted fork
  (`head.repo: null`) is treated as a fork. `merge-method` is trimmed, case-insensitive, and an
  unknown value warns before falling back to `merge`.
- Fewer and parallel API calls: auth checks, the comment thread, the root OWNERS and the Octokit
  client are memoized per run; config probes, OWNERS probes and label removals run concurrently.

## App server (beta)

- `POST /webhook` is capped at 25 MB (`413`); App-level events with no repository get `202 ignored`
  instead of a `400`; a failed delivery is forgotten so GitHub's redelivery runs it again (Node,
  Redis and Cloudflare KV stores alike).
- Redis locks renew while a handler runs; waiters back off with jitter; `/readyz` answers `503`
  whenever Redis is not ready and during the `PROW_SHUTDOWN_DRAIN_MS` drain on `SIGTERM`.
- Cloudflare Worker: one platform scope per isolate, a real per-pull-request lock in the Durable
  Object, a retrying queue path with a dead-letter queue (`prow-jobs-dlq`), and tokens minted only
  where they are read.

## Upgrading

Nothing to do for the action. Helm users: the chart's Deployment, Service and PDB now select
`app.kubernetes.io/component: server` so CronJob pods never receive webhook traffic. A Deployment's
selector cannot change in place, so delete it once before `helm upgrade` (see
[Kubernetes](https://github.com/cncf/prow-github-actions/blob/v3.5.0/docs/github-app.md#kubernetes)):

```sh
kubectl delete deployment prow-prow-github-app   # <release>-prow-github-app
helm upgrade prow oci://ghcr.io/cncf/prow-github-actions/charts/prow-github-app --version 3.5.0 …
```

The chart also raises `terminationGracePeriodSeconds` to 75 and adds `cronjob.activeDeadlineSeconds`
(default 3000); `values.schema.json` now rejects unknown keys.
