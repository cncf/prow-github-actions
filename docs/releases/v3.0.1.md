# v3.0.1

A patch for three things the scheduled path did to one pull request (cncf/automation#709): a
deadlock between `/approve` and the merge gate on pull requests opened before the OWNERS files
landed, a fork merge GitHub refuses that failed every run, and a double evaluation under
`jobs: sweep lgtm`. No new features, no configuration changes.

## Fixes

Symptom | Cause | Fix | What you see
--- | --- | --- | ---
`/approve` on an older pull request posts a bot review instead of the `approved` label, while tide logs `skipping pr #N: missing approved`; only a rebase or a hand-applied label unblocks it. | `/approve` read the OWNERS files at GitHub's `base.sha`, a snapshot of the base from the pull request's last update, which predates the OWNERS files; the gate's `[lgtm, approved]` default came from the default branch's *current* tree. Two probes, two refs. | Both read the **current tip of the pull request's base branch** (one `GET /branches/{base}` per branch per run, memoized). The gate is resolved per pull request from that same branch, on events, in the `lgtm` cron and in the `sweep`. | Pull requests opened before OWNERS landed get `approved` through `/approve` without a rebase; the `[APPROVALNOTIFIER]` OWNERS links point at the base branch tip; a base branch whose OWNERS files were removed drops back to the `[lgtm]` gate and the legacy `/approve`. Nothing ever reads OWNERS from the pull request's head.
A fork pull request passes the gate, `lgtm` bound, `mergeable_state: clean`, and every scheduled run fails with `PUT /merge → 403 Resource not accessible by integration`; no branch protection or ruleset explains it. | A GitHub App token, `GITHUB_TOKEN` included, may not merge a fork pull request when the merge involves `.github/workflows/*` changes the fork's head does not contain (or that the pull request makes): GitHub demands the `workflows` permission, which `GITHUB_TOKEN` cannot have (bors-ng/bors-ng#806). #709's head was one commit behind `main`: the one that added the workflows. | On a fork 403 the merge path compares the head with the base and lists the pull request's files (one call each, only then). When either names a workflow file it comments once per head with the files and the way out, warns, and **skips** the pull request instead of failing the run ([docs](https://github.com/cncf/prow-github-actions/blob/main/docs/automatic-merging.md#fork-pull-requests-and-workflow-files)). | One comment on the pull request: rebase onto the base branch, merge by hand, or pass a `token` with the `workflows` scope. The cron and the sweep stop erroring on it. A 403 without workflow files, or on a same-repository pull request, still fails with GitHub's message.
Under `jobs: sweep lgtm` (both templates) a pull request gets two `PUT /merge` attempts and two error annotations per scheduled run. | The `sweep` and the `lgtm` cron both reach every pull request the sweep considers a candidate, and each evaluated it. | The scheduled jobs evaluate each pull request once per run, whichever gets there first; event handlers never dedupe (a comment and a labeled event in one run are distinct evaluations). | `skipping pr #N: already evaluated in this run` from the job that came second; one merge attempt.

## Upgrading

Nothing to do. `@v3` callers get it automatically; `@v3.0.0` pins move to `@v3.0.1` (Dependabot
proposes it; the templates ship it). Behaviour on pull requests whose base branch is not the
default branch now follows *that* branch's OWNERS files, as Prow does.
